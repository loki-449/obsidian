## 三、流量路径图（真实版）

### 日常运行时

```

  └→ 本地代理设置指向 127.0.0.1:15721
     └→ CC Switch (PID 25404)
        ├─ 协议翻译（Anthropic → OpenAI 格式）
        ├─ 路由到第三方 API（DeepSeek: api.deepseek.com）
        └─ CC Switch 自身出站
           └→ 走 TUN/系统代理 → mihomo 内核

     └→ 或直接走 TUN/系统代理 → mihomo 内核
```

| 工具 | 本地代理设置 | 经过 CC Switch？ | 出站走 OK CLOUD？ |

## 四、CC Switch 角色详解

### CC Switch 是什么

CC Switch（:15721）是一个**本地 API 翻译代理**，核心作用：

```
Claude Desktop 的请求格式（Anthropic API）
    ↓
CC Switch 翻译（改变 endpoint、鉴权、模型映射）
    ↓
转发到第三方 API（DeepSeek: api.deepseek.com/v1）
```

### 为什么需要它

| 问题 | CC Switch 的解决方式 |
|:----|:-------------------|
| Claude Desktop 只认 Anthropic 官方案例 | 劫持 Claude 的 network 请求，重写 endpoint 到第三方 |
| Codex 只认 OpenAI 格式 | 适配 OpenAI API 格式 |
| 你想用 DeepSeek 而不是 Anthropic/OpenAI 官方 | 路由到 api.deepseek.com |
| 模型映射 | 例如 Claude Haiku → DeepSeek V4 Flash |

### CC Switch 接管了谁

从数据库确认：
- **Claude Desktop** → 已接管（proxy 模式）
- **Codex** → 已接管
- **Gemini** → 已接管

## 五、端口冲突风险评估（真实情况）

### 会不会打架？

```
你现在运行的进程：
  mihomo-windows-amd64.exe (32392)  ─ 7890, 7891, 7892
  cc-switch.exe (25404)             ─ 15721
  claude.exe (30996)                ─ 不占服务端口（客户端）
  OKCLOUD.exe (34060)              ─ GUI 界面，不占服务端口
```

### 真实风险评估

| 场景 | 会打架吗？ | 理由 |
|:----|:----------|:----|
| **Claude ↔ CC Switch** | ❌ 不会 | Claude 是客户端出站，不占端口 |
| **Codex ↔ CC Switch** | ❌ 不会 | 同上 |
| **CC Switch ↔ mihomo** | ❌ 不会 | 各自用不同端口段（15721 vs 7890） |
| **两个 AI 同时用** | ❌ 不会 | 各自独立的出站连接，不抢端口 |
| **关 OK CLOUD 后** | ❌ 不会打架，但功能受限 | CC Switch 出站可能连不上 DeepSeek |
| **未来装 Docker** | ⚠️ 9090 可能撞 | 解决方案：OK CLOUD 管理 API 改 9091 |
| **未来 WSL2** | ⚠️ 53 可能撞 | 解决方案：Clash DNS 改 1053 |

### 实际结论

> **你当前的系统完全没有端口冲突。** 所有程序的端口段天然分离：
> - 7890-7892：mihomo 内核（代理层）
> - 15721：CC Switch（翻译层）
> - 其他：客户端程序，不占服务端口

**唯一需要记住的规则**：以后在 Cursor 终端跑 Jupyter/Flask 等服务时，避开 7890-7899、15721、9090-9099 这几个段即可。

| 项目 | 设置值 |

| TUN 模式 | **开启**（兜底所有不走系统代理的流量） |

### DNS 配置

| 选项 | 设置值 | 理由 |
|:----|:------|:----|
| 覆盖系统 DNS | ✅ 开启 | 避免 ISP DNS 劫持 |
| 关闭后使用系统 DNS | ✅ 开启 | 关 Clash 后回退到系统 |
| 使用系统的 DNS | ❌ 关闭 | 防止 ISP DNS 参与境外域名解析 |
| IPv6 | ❌ 关闭 | 代理线路不支持，开着可能泄露 |
| DNS 链接跟随 rules | ✅ 开启 | **核心**：国内域名用国内 DNS，境外走代理查 |
| nameserver | 223.5.5.5, 119.29.29.29 | 阿里 + 腾讯 |
| default-nameserver | 223.5.5.5, 119.29.29.29 | 同上 |

## 七、排查速查

### 网络不通时的排查顺序

```
① 浏览器能打开百度吗？
   ❌ → 物理网卡断了，检查 WiFi/网线

② 浏览器能打开 ip.sb 吗？
   ❌ → OK CLOUD 开着吗？TUN 开着吗？

③ Claude Desktop / Codex 能用吗？
   ❌ → CC Switch (:15721) 开着吗？
   ❌ → 检查 CC Switch 设置里的 provider 是否正常

④ Cursor 能用吗？
   ❌ → 检查 Cursor 的代理设置指向哪里
```

### 各工具代理设置位置

| 工具 | 设置路径 |
|:----|:--------|
| **CC Switch** | `%USERPROFILE%\.cc-switch\settings.json` / DB 配置 |
| **Claude Desktop** | 由 CC Switch 接管，自动注入代理配置 |
| **Codex** | 由 CC Switch 接管，自动注入 `.codex/config.jsonc` |
| **Cursor** | 设置 → 搜索 proxy / 系统代理 |
| **OK CLOUD** | 界面操作（规则/TUN/端口均在 UI 中设置） |

### 端口占用的快速自查命令（CMD）

```cmd
:: 查所有关键端口
netstat -ano | findstr ":7890 :7891 :7892 :9090 :15721 :53"
```

## 八、重装/换机恢复步骤

1. 安装 OK CLOUD → 模式切"规则" → 开启 TUN
2. 添加自定义规则（见第六节）
3. 配置 DNS（见第六节）
4. 安装 CC Switch → 自动恢复配置（或从备份导入）
5. 验证：浏览器 ip.sb ✅、Claude 桌面端 ✅、国内网站 ✅
